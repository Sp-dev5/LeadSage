# Features and commands

Everything LeadSage does, part by part, and every command. The [README](../README.md) has the short version.

## Parts

- **The web app** (`web/`, run with `uvicorn web.app:app`): four pages (Home, Leads, Outreach, Ideal customer) in plain HTML and CSS with the fonts served from the app itself, so it makes no outside requests. Set `LEADSAGE_PASSWORD` in `.env` to ask for one shared password before any page opens (without it the app is open, so keep it on localhost). With a password the app also needs a long random `LEADSAGE_SECRET` (it will not start without one); five wrong passwords lock the login for 15 minutes, and `LEADSAGE_HTTPS=1` makes the session cookie HTTPS-only once it runs behind HTTPS. Every form carries a token, so another site can't post in your name. Scoring and drafting run in the background and show their progress at the top of the page. On the **Ideal customer** page every part of `data/icp.json` can be edited: the three descriptions (a suggestion for a fuller wording appears a moment after you stop typing, plus other job titles for the buyer, and nothing changes until you click Use this), size range and countries, the four weights and every cut-off, the rules that send a lead to review or disqualify, the industry table, the gates and the sales job titles. Each save is checked against the same rules the scorer loads with, so a value that can't work is refused and nothing is written. Rescore the leads after a change.
- **Company logos** (`agent/logos.py`): the icon each company's own homepage declares, saved in `data/logos/` (not committed). No logo service is used. Companies whose site gives none show an initial. `python -m agent.logos` fetches them for stored leads, and the pipeline fetches one for each new lead.
- **Website** (`site/index.html`): a one-page site that explains the product and links to the web app (port 8000). Same notebook look and colours as the app (neutral black, sage-mint highlighter), with a dot spotlight that follows the cursor; fonts stored in `site/assets/fonts/`. Plain HTML, CSS and a little JavaScript, no build step.
- **Finding companies** (`agent/find.py`): pulls real companies from the open Y Combinator company list (free, no key) into a lead CSV with every column filled: name, industry, team size, location, website and a one-line description. It keeps active companies whose team size is inside the ICP's range (`--any-size` turns that off) and skips any company already in the lead store or in a lead CSV. `--in-region` keeps only companies with a location in the ICP's countries, and `--hiring` only those the list marks as hiring now. The sample is repeatable (`--seed`), and an existing file is never overwritten, so labels can't be lost. The list leans to young, US-based startups.
- **Pipeline and lead store** (`agent/pipeline.py`, `agent/store.py`): reads each company's website, finds open sales roles, scores it and saves the result in a local SQLite file the app reads.
- **Outreach** (`agent/outreach.py`, `agent/contacts.py`, the Outreach page): finds the person to write to on the company's own about and team pages, drafts a short first email and up to 3 follow-ups, and tracks each lead's stage (new, drafted, approved, contacted, replied, meeting, lost). Every sentence about the prospect must quote their own website or job posts; sentences without a real quote are cut, and each kept one shows its source and date. A first email should open with a hook, a timely reason to write: the company is hiring salespeople, or its own news page shows something recent (a launch, a partnership, a new hire). Drafts with no hook are flagged so a person adds one before sending. A person approves every email and sends it from their own mailbox; a reply stops the follow-ups. Sender, follow-up days, the daily sending cap and which leads get emails live in `data/outreach.json`.
- **Sending and replies** (`agent/mailer.py`, the Outreach page): with your mailbox settings in `.env` (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`; a Gmail or Outlook app password works), an approved email gets a Send button. It goes out exactly as approved, from your address, to the contact's address that you typed in (LeadSage never guesses one), one at a time and at most `max_sends_per_day` a day; follow-ups stay in the same thread. With `IMAP_HOST` as well, Check for replies (and every full `python -m agent.watch` run) searches your inbox, read-only, for answers from contacted leads only. A reply stops the follow-ups; one that says unsubscribe, stop, remove me or not interested also puts the company on the do-not-contact list. Out-of-office replies are ignored. Only the start of each reply (500 characters) is kept. Without these settings nothing changes: you send from your own mail program and click I sent it myself.
- **CRM import** (Leads page, Move to a CRM): a CSV of the leads you pick (verdicts, stage) with HubSpot's import column names: Company name, Company domain name, First name, Last name, Job title, Email, Lifecycle stage, plus LeadSage fit, verdict, stage, why and source. HubSpot imports it as is (Contacts, Import, file from computer); in Zoho CRM or Pipedrive, map the same columns by hand on import. LeadSage stores no CRM password.
- **Hosting** (`deploy/`): a guide and a setup script to put the website and web app on a free Ubuntu server behind HTTPS, with the models staying on your laptop over Tailscale. See `deploy/README.md`.
- **Lead scoring** (`agent/score_lead.py`): scores a company against the ICP with evidence for every number. Facts like size and country are checked in code; the model only judges buyer and pain. A company under the minimum headcount, or above the largest size times `max_size_factor` (both in `data/icp.json`), is dropped without asking the model for buyer and pain. The fit weights and cut-offs in that file are plain numbers for the fit average: the model never sees them. Reading facts out of a company's text (what it sells, who it sells to, whether it is a non-profit or a government body) and the buyer and pain judgement both run at temperature 0, so a rerun usually gives the same score. It is not exact: a lead scored on its own can come out differently from the same lead scored in a batch. Freelancers and sole proprietors who buy as a business count as businesses, and a non-profit or government body goes to review, not to disqualify.
- **Model layer** (`agent/llm.py`): local open-source models through Ollama do the scoring, so nothing leaves your machine. Optional: with a free Groq key in `.env` (`GROQ_API_KEY`), the email drafts are written by a larger model on Groq's free tier; only the drafting prompt (public website text about the company, the contact's name and title, and your pitch) is sent. Without a key, or if Groq fails, the local model writes them. If a local model crashes, times out or returns broken output, the question goes once to the other local model (`OLLAMA_FALLBACK_MODEL` to choose); a lead scored that way says which model scored it and stays at review. The ideal-customer suggestions use the main model unless `OLLAMA_SUGGEST_MODEL` is set.
- **Evaluation** (`agent/evaluate.py`): grades the scorer against hand-labelled leads. With `--text fetched` it scores the company's real website instead of the typed description.
- **Fetcher** (`agent/fetch.py`): reads a company's web page and returns the text with its source and date. It checks robots.txt first, including at every redirect. A failed fetch never stops a batch.
- **Sales hiring** (`agent/signals.py`): reads a company's open jobs from its job board (Ashby, Greenhouse, Lever, Keka, Trakstar, Kula; found on the careers page or typed in the CSV) and finds the sales roles. A title counts if it contains one of the ICP's sales titles, or if the model says it's a sales role and the title really is on the list. Each role keeps its source and date. Found roles tell the scorer the company has salespeople.
- **Signal watcher** (`agent/watch.py`): reads each lead's job board and news pages again and flags what is new since the last look: a sales role not seen before, or a news item from the company's own site dated in the last 14 days (`fresh_days` in `data/outreach.json`). A plain blog post never counts, the same rule as for email hooks. The first look at a lead only records what is there, so nothing fires on day one. A board or page that can't be read counts as unknown, never as "no roles". Leads with a new signal move to the top of their tab on the Leads page; news never changes a score, and a lead is rescored only when its set of sales roles changes, since roles were already part of the score. Hiring is watched for companies listed in `data/signals_leads.csv`; news only for leads whose verdict gets an email.
- **Funding news** (`agent/press.py`): each full watch run also reads Inc42, YourStory and Entrackr and keeps the headline, link and date, never the article. A headline counts only if the lead's full name comes directly before a raise word and an amount or round ("Acme Labs raises $5 Mn"), so results stories and talks of a raise stay out. A one-word name also needs the lead's domain or city in the article's opening, which is read once and not kept. A match can open the first email, quoted as reported by that outlet, for 90 days. It never changes a score, and strict matching means some real rounds are missed.
- **Sites we can't read**: three honest routes, and no way around a site that says no. When a site can't be read, the company's Wikipedia summary is used if the page is a real article about a company (`agent/wikipedia.py`; many names land on something else, and those are refused). The rep can paste text from their own browser on the lead, and the scorer uses it with the same quote checks, labelled "pasted by the rep". The watcher checks each website weekly: one that can't be reached shows as down, and two checks in a row suggest marking the lead lost. A careers page with no supported job board is read for its `JobPosting` data instead. JavaScript-only sites are not rendered: a headless browser would load pages past the check that refuses internal addresses, so the paste box covers them.
- **Personal data** (built with India's DPDP Act in mind, not legal advice): the contact card says where a name came from and when, and "What we hold" lists every stored field about that person. An optional `notice_line` in `data/outreach.json` goes under the signature of first emails. A reply asking to delete their data removes the person, the emails to that company, the details of its replies and the saved copies of its team, news and home pages, and keeps the company on the do-not-contact list. A person never emailed is forgotten after `forget_after_days` (180 by default; 0 keeps them), along with the same saved pages.
- **What the agent did** (`agent/trace.py`): every step on a lead is kept and shown on its card, in order: each model call with its full prompt and answer, the pages read, the quote checks with what was kept and cut, the rules that fired, the fit and verdict, the second opinion, the contact search, the proof points found, and approve, send and reply. A step opens to show the prompt and the answer as plain text. The last 3 runs of each kind (scoring, email, watch) are kept per lead (`trace_runs_per_lead` in `data/outreach.json`). The trace copies page text and names, so deleting a lead, a delete request and the 180-day forgetting remove it too, and What we hold lists it. It is never fed back to a model.
- **Your documents** (`agent/kb.py`, the Ideal customer page): upload case studies, product notes or answers to objections (text, Markdown or PDF; 10 MB and 200 pages at most). They are split into passages and indexed on your machine with a local embedding model (`nomic-embed-text`), kept in the lead store. When a lead looks like a passage (`kb_top_k` 3 closest, at least `kb_min_similarity` 0.75), the email writer may add one proof sentence after the pitch. It goes through the same check as a line about the prospect: its quote must be in the passage, every name and number in it must be in the passage, and a line that reads like an offer (a discount, a price) is cut. The card shows "your document: file, page n". A follow-up never reuses a passage. Passages go to the cloud model only if `kb_send_to_cloud` is on; otherwise that draft is written by the local model. A passage that addresses an AI ("ignore your instructions") is kept out of every prompt. Draft from my documents fills the three descriptions from the passages, each sentence with its quote and file, and nothing changes until you click Use this. Scores never read the documents. Scanned PDFs (pages with no text) give no passages, and the list says so.
- **Careers probe** (`agent/fetch_careers.py`): a feasibility check for the hiring signal. It fetches each careers page from `data/signals_leads.csv` (columns `name,careers_url`) and reports whether the page is readable and mentions sales roles. It passes if at least half do.

## Test results in detail

Scored with the final rules on local models, November 2026:

| Set | Text scored | Agrees | Near | Wrong |
|---|---|---|---|---|
| 47 hand-labelled companies, mostly made up for testing | typed description | 35 | 11 | 1 |
| 50 real companies, labelled from the ICP's rules by a separate AI model | website text | 39 | 11 | 0 |

Near means one verdict away: review against qualify or disqualify. These numbers show the scorer follows the ICP's rules. They don't show the rules are right, and nothing here proves replies or revenue: no real campaign was run. A possible competitor goes to review, not disqualify: the model sometimes calls a company a sales-tool seller when it isn't (Rocketlane, Everstage), and a quote check confirms the words exist, not what they mean. The cost is that real competitors in the test sets now land in review, which counts as near. A rep reads every lead and every draft before anything goes out.

Your documents, tested with the made-up sample (November 2026): 10 of 10 test searches, written before the first run, found the right passage first. On the 15 real leads closest to the sample, only one was close enough to be offered a passage, and the model did not use it, so the sample changed none of those 15 emails. A made-up payroll company that matches a case study got a checked proof line in one of two drafts on the local model. A planted "90% discount" line was kept out of the index, and when forced into the prompt it still never reached an email. Scores did not change: the 47 labelled companies came back 35, 11 and 1 again. How much real case studies help depends on how close your customers are to your leads.

Sending and replies, tested end to end (November 2026), on a copy of the lead store. Through real Gmail: the app logged in, sent an approved draft to a test address, then found a "not interested" reply in the same thread over IMAP, put the company on the do-not-contact list and stopped its follow-ups; a second check found nothing new. The reply was sent from the same account, not by a separate person. Against a mail server on the laptop, over TLS with its certificate checked: an unapproved email was refused before the server was touched, and the email that arrived matched the approved subject and body word for word.

## Commands

```bash
pip install -r requirements.txt
ollama pull qwen3.5:9b            # local model (default)
ollama pull nomic-embed-text       # local embedding model, for your documents
python -m agent.find --industry B2B --limit 50    # pull real companies into data/found_leads.csv
python -m agent.find --industry B2B,Fintech --in-region --out region_leads.csv   # only your ICP's countries
python -m agent.pipeline --file real_leads.csv   # research + score into the lead store
python -m agent.outreach --draft  # find contacts and draft first emails
python -m agent.outreach --follow-ups            # draft follow-ups that are due
python -m agent.watch             # look for new sales roles and news (--hiring-only skips news)
python -m agent.kb                # index your documents in data/kb (--folder data/kb_sample for the made-up sample, --check for the search test)
uvicorn web.app:app --host 127.0.0.1 --port 8000            # the web app, at http://127.0.0.1:8000/
python -m agent.logos             # fetch company logos for stored leads
python -m http.server 8600 --directory site                 # the website, at http://127.0.0.1:8600/
python -m agent.score_lead        # score a sample company
python -m agent.evaluate          # grade against the labelled leads
python -m agent.evaluate --file real_leads.csv --text fetched   # score real websites
python -m agent.fetch https://example.com                       # read one page
python -m agent.fetch_careers                                   # probe careers pages
python -m agent.signals                                         # sales roles from job boards
```

Run the tests with `pip install -r requirements-dev.txt` then `pytest`.

The ICP lives in `data/icp.json`. Change it on the Ideal customer page, or in the file, to score for a different customer.
Swapping models only touches `agent/llm.py`; nothing that calls it changes.

## Roadmap

1. Lead scoring (done)
2. Walking skeleton: research, score, contact, cited email, follow-ups (done)
3. Scoring engine: signals move a lead up the queue; a separate intent score was not built, because no outcome data exists to check it
4. Signal watcher: new sales roles and news move a lead up the queue (done; runs when you start it, or on a schedule you set up)
5. Approval before sending, one-click send from your own mailbox, reply detection (done)
6. CRM: import file today; a live sync would need a CRM account and key

## A few terms

| Term | Plain meaning |
|---|---|
| **Lead** | A company or person who might buy. |
| **ICP** | Ideal Customer Profile: a description of the perfect customer. |
| **Agent** | An AI that does a job in steps on its own (search then read then write). |
| **CRM** | Software sales teams use to track customers. |
